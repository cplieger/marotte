# Features

This page describes each part of the marotte page. Everything here works from any device that opens the same server, and every action the page takes is an endpoint of [the HTTP API](api.md).

## Chat

Conversations stay in sync across devices, so a chat open on a phone and a desktop shows the same messages. Replies stream in as formatted text, and the agent's reasoning shows in blocks you can fold.

- Send a message while the agent is working and it joins the running turn, or with **Queue messages** switched on in the composer's **Chat options** menu, runs after it. Queued messages send one per turn, in order, and each row above the composer says how many turns it waits. Its up arrow stops the reply and sends that message next, ahead of the others, or sends it at once when nothing is running. On a touch screen, Return adds a new line, so send it with the **Steer** or **Queue** button beside Cancel.
- `/clear` opens a fresh chat and leaves this one in its tab. `/compact` compacts the context now, or at the end of the running turn, waiting above the composer with a button to cancel it. Once it starts, the row above the composer says **Compacting the context…** with a spinner and no cancel button until it ends: a **Conversation compacted** mark shows where it compacted, and a notice shows when it did not run. A cancel sent after it started, from another device for example, does not stop it, and the row stays until it ends. A message you send while it runs waits in the queue under it and goes when the compaction ends, after any message already waiting there. After a turn you stopped or the model refused, the messages that turn left waiting go only after the next turn, and anything you send afterwards goes ahead of them. A compaction ending does not send them either. A message the agent had not read when you stopped the turn waits under the compaction too, and goes first when it ends. Pressing a row's up arrow while the compaction runs does not stop it: that message goes first when it ends. Cancel never stops a compaction on its own. If the agent started a turn during one, cancelling that turn restarts the compaction after it. If the agent's turn never marked its start, the compaction closes that turn first and then runs. Each row says when it goes. `/drop` ends a turn that is stuck. `/goal` sets an objective the agent works toward across turns, until it meets the goal or runs out of attempts. `/model`, `/agent`, `/context`, `/usage`, `/stats`, `/tools`, `/mcp` and `/help` open the control that shows that state: the model, mode or context pill, Settings, or the `/` menu. `/model` followed by a model id switches to that model. Other kiro-cli commands, such as `/theme` or `/hooks`, are not sent to the agent, and a notice says which control does that job here.
- **Compact automatically** in Settings compacts a long chat at the **Compact at** point, from 50% to 90% of the context. When a turn reaches the point, a compaction waits above the composer, where you can cancel it, and runs as soon as the turn ends, before any queued message. The waiting row then turns into the running one, which goes when the **Conversation compacted** mark appears, or with a notice if the compaction did not run. A page reloaded during a compaction shows the running row. Nothing compacts during a turn, so one very long turn can still reach the context limit. The chat is then compacted when that turn ends, and you send the message again. If you cancelled that turn's compaction, its end does not compact: press **Compact the context** on the notice, or compact from **Chat options**.
- A Mermaid diagram in a reply (a fenced `mermaid` block) is drawn as a picture. Its buttons switch to the source, copy it, download the SVG, or open the diagram full screen, where a pinch, the mouse wheel or the zoom buttons enlarge it. A diagram that cannot be drawn shows its source with a note saying why.
- When the agent loads steering docs, a **Steering loaded** box names them where they were loaded: the always-included docs at the top of the chat's first turn, and a doc that a file read or edit brings in beside that tool call. Each doc in the workspace shows as a file link that opens it in the editor. A doc outside the workspace, such as one in `~/.kiro`, and the doc marotte itself sends, named `marotte`, show their name only. A group of these boxes counts the docs, as in "Loaded 3 steering docs: marotte, mandatory-instructions.md, +1 more". The box has the same compass icon as **Steering** on the `/docs` page, and hooks have the same fish-hook icon in the chat and on the `/docs` page.
- Two or more tool calls or steering boxes in a row share one box whose header counts them, such as "Ran 2 commands: go vet, go test". The box folds once something follows it. A single tool call or steering box keeps its own box, with no header. Hooks never count toward a group.
  - A hook that passes and prints nothing folds into a fish-hook badge at the top right of the box's first line: the group header, or the single tool call's own line. The badge opens a list of the hooks with how many times each ran. A group's badge lists the hooks it folded. A single tool call's badge lists all of its hooks, those that keep a row included.
  - A hook that failed or printed something keeps its own row inside the box. A tool call that failed or was refused also keeps as rows its PreToolUse and PostToolUse hooks and any hook whose trigger kiro-cli has not reported, since kiro-cli does not say which hook refused it. Its other passing hooks stay on the badge.
  - A delegate's card and a workflow run's card carry the hooks of the call that started them the same way. That call's quiet PreToolUse hooks, between the card and the agent's text or the card before it with no other tool call in between, and its PostToolUse hooks, just after it, fold into a badge on the card's header, which lists them all. A hook right after another tool call stays with that call, since a file write's hooks are recorded after the write. If that call failed or was refused, they keep their rows.
  - A quiet hook that runs at turn start or turn end, away from any tool call, folds into the badge of the nearest box or card in its turn. That is the one before it, or the first one after it when none comes before. A quiet PreToolUse or PostToolUse hook that sits apart from its tool call, past the agent's text, keeps its own row.
  - Hook rows with no tool call between them share one box with no header. In a turn with no tool call, steering box, delegate's card or run's card at all, two or more of them share a box headed with their count, such as "Ran 2 hooks". No badge shows there.
  - With **Show hook status in chat** off in Settings, the badge is hidden, and so is every quiet hook but the PreToolUse and PostToolUse hooks of a call that failed or was refused.
- Attach files by drag and drop, paste or the composer's **Chat options** menu. PDF, CSV and Office documents reach the agent as documents and images as images. Any other file reaches it as a path it opens with its file tools.
- Select text in the conversation and a **Quote in reply** button appears beside it. It adds exactly that text, its indentation and line breaks included, up to 1,500 characters, to the message box as a quote you can edit. A line above the quote names where it came from, such as "From the output of `go test ./...`". Your sent message then shows the quote and its source as one line above your question, whether its turn is open or folded.
- **Ask in a tangent**, beside **Quote in reply**, starts a [tangent](#agent-control) with the quote already in the tangent's message box. Until the chat has a message, it is off and says why, as **Start a tangent** in **Chat options** does.
- Both buttons appear for text in replies, your own messages, turn headers, tool cards, hooks and steering boxes, the agent's reasoning, workflow messages and workflow cards, and the run list above the message box. Neither appears for a button or menu label, or for a selection that spans two sources, such as a reply and the tool card after it.
- A shell code block in a reply has a **Run in shell** button that sends it to the shell panel and presses Enter. A block of several lines asks first and shows all of it, then runs as one input, as if you had pasted it and pressed Enter once. A `#!` script has no Run button. Run never sends characters you cannot see. Whitespace around the command is dropped, and the button is off when the command still holds such characters, such as direction marks, zero-width characters or a tab, so copy the command to inspect it. A one-line command wider than the block also asks first and shows all of it.
- Closing a chat tab that still has work running asks first and names what stops: the reply, a question waiting for you, its workflow runs and its queued messages. Closing an idle chat does not ask.
- **Output style** in **Settings** lists the response styles kiro-cli offers, such as Concise, Explanatory or Learning, each with kiro-cli's description. A new style applies from your next message on.
- **Clock** under **Display** on the **General** tab in **Settings** picks how times of day are shown: **Automatic**, **24-hour** or **12-hour**. Automatic follows your browser's languages, or its operating-system time format where the browser offers one, as Firefox does. The choice is kept in the browser, so each device keeps its own, and a change redraws the clock times already shown in chats at once. Other times, such as file dates and schedules, follow the new choice the next time they are drawn.

You can also search inside a chat, export a chat, search across chats, and browse past conversations and workflow runs in **History**. Both searches find a message, tool card or prompt holding every word you type, in any order, ignoring case and accents (**Match case** in Find in chat makes it exact). Put words in quotes to match them as an exact phrase. Find in chat opens only the turn and the sections that hold the match you are on, and folds them again when you move on or close it. Settings decides how long closed chats are kept. With **Days kept** above 0, finished workflow runs are deleted that many days after they last ran, even while their chat stays open.

## Agent control

- Switch modes: Default, Spec, Quick Spec, Bug Fix, Plan and Autonomous, or the bundled Semantic Reviewer agent, plus your own agents from `.kiro/agents/` in the workspace or in your home folder.
- Switch models during a conversation, and set reasoning effort from low to max.
- Answer permission requests, the agent's questions and the forms an MCP server asks you to fill in.
- Allow a permission request once, with **Allow for this chat**, or with **Always allow**. **Allow for this chat** keeps the rule only while the chat's session runs, and saves nothing. Only **Always allow** saves the rule, and it switches **Permissions** to Custom.
- Fork a tangent, a new chat that starts with this chat's context and leaves the original untouched. **Branch from here** on a turn starts one with the conversation up to that turn. The files on disk are not rolled back. **Merge into parent chat** in the composer's **Chat options** menu, or `/tangent merge`, sends a summary of the tangent's findings back to the chat it came from.

Pressing Stop on a reply answers that reply's open permission requests as cancelled, and their cards close as part of the stop. A card from a workflow step running in the same chat stays open, because Stop does not stop the workflow.

The **Workflows** switch in Settings decides how the agent hands work off. On: the agent can start workflows that run in the background while you keep chatting, and **Workflow use** says when: only when you ask, the default, only for large tasks, or as much as possible. Off: it uses subagents instead and waits for each to finish before it continues. Either kind of handed-off work shows as a card you can open on its own page. A question a workflow step asks goes to the agent that launched the workflow, not to you: the chat shows that the run is waiting for an answer, and to answer the step yourself, open the run's tab. The box above the message box lists the live runs the chat started, each with its progress, and a line opens the run's tab. With two or more runs, a header row on top counts them and folds or opens the list, and **Pause all** at its right end pauses every running one at once. Two runs start with the list open and three or more start folded, until you fold or open it yourself; each device remembers that choice. A single run shows no header: a **Pause** button at the right end of its line pauses it, and turns into **Resume** once it is paused. Pausing cancels each run's current turn, and the run picks up from there when resumed. Once none is running, the button turns into **Resume all**, which resumes the runs you, an agent or the chat paused, and the runs a rate limit or another passing model error paused. **Resume** follows the same rules for its one run. A run waiting for an answer or stopped at a loop's pass limit stays paused, since it needs your decision. If some runs refuse, one message names them. A step's permission requests still come to you in the chat. The agent's own terminals show their output on the tool card that started them.

## Kiro account

The agent uses the Kiro account you sign in with on the page, with AWS Builder ID or IAM Identity Center: marotte shows a code, and you approve it in your browser. The sign-in is marotte's own. marotte never reads the sign-in of a `kiro-cli` you start in the terminal, and the two can be different accounts. If you used marotte before it kept its own sign-in, sign in once more after updating.

An IAM Identity Center account needs a Kiro profile, and without one the sign-in says "This account has no Kiro profile marotte can use". A Builder ID account signs in with or without one. When a sign-in fails after the browser step, the dialog says why instead of waiting. marotte reports the account's class the way kiro-cli does, so an organization's governance applies as it does in kiro-cli.

The account menu shows the sign-in method, start URL and region, and the account's email when Kiro's account service returns one at sign-in.

Signing in as another account reaches every open chat and running workflow with no restart. kiro-cli asks marotte for the account again at its first model call a minute or more after its last ask. That call can still use the previous account while kiro-cli renews in the background, and the call after it uses the new one. A call made after the previous account's token expired, about four minutes after the last ask, waits for the renewal and uses the new account.

Two kinds of switch wait for the agent engine to restart, because kiro-cli would keep part of the old account: a switch from an account with a Kiro profile to one without, and a switch between account classes, such as Builder ID to IAM Identity Center. The restart banner then says "The new Kiro account applies after the agent engine restarts". Until the restart, chats keep using the previous account whole, and signing in to the previous account again clears the banner.

Signing out stops the account within about four minutes, because kiro-cli keeps a token it already holds until it expires. **Restart now** under **Agent engine** in **Settings** stops it at once. If marotte cannot remove the saved sign-in, signing out says so and you stay signed in.

## The agent engine

One agent engine runs every chat and workflow. **Agent engine** on the **General** tab in **Settings** holds **Restart now** and **Agent engine memory limit**, which caps the engine's JavaScript heap and is empty by default, leaving kiro-cli's own limit of about 4 GB.

These settings apply only when the engine restarts, and their rows say so: **Knowledge base search**, **Model fallback**, **Steering reminders**, **Auto model routing**, **Smart helper models**, **AWS CloudFormation safety check**, **kiro-cli telemetry**, **Agent engine memory limit**, **High throughput optimizations** and the engine's part of **Debug logs**. After a change, a banner names them, and the engine restarts by itself as soon as no reply and no workflow is running; while `config.json` cannot be read, it waits until the file reads again. **Restart now**, in the banner or in **Settings**, asks first and names the chats whose reply would stop and the workflows that would pause. Those workflows resume by themselves once the engine is back. [How marotte works](how-it-works.md#the-agent-engine) describes restarts and crashes.

## Files, editor and terminal

- A file browser with a search that finds files by name, or inside files when you ask. One Files filter narrows either search (`*.css`, `src/**`, `!node_modules`), and files your `.gitignore` excludes stay out unless you include them.
- An editor with syntax highlighting. A link can point at one line with `#L<n>`.
- A preview tab that shows an HTML page from the workspace in a sandbox, at phone, tablet, desktop or full width. Clicking an `.html` or `.htm` page that sits in its own folder in the file browser opens it there, and so does a link to one in the chat. **Edit** in the tab's bottom bar opens the page's source in the editor, and the editor's **Open preview** button goes back to the page. The tab reloads when the page's files change.
- Diffs against the last save or against git `HEAD`.
- A merge-conflict view that takes ours, theirs or both for each hunk.
- A terminal, built on [web-terminal-engine](https://github.com/cplieger/web-terminal-engine), that survives sleep and network drops.

## Git and forges

marotte works with GitHub, GitLab, Codeberg, and Gitea or Forgejo. You can stage, commit, diff and switch branches, and list, create, merge and close pull requests. A new pull request's description starts as the list of the branch's commits, which you can edit before you open it.

An account connects by signing in through your browser on GitHub or GitLab, or with an access token on any of them. marotte keeps the credential in its own store, uses it for the forge's API, and answers git over HTTPS with it through its own credential helper, so no forge command-line tool is needed. SSH remotes are not covered. A forge on a private or loopback address, such as one on your own network, needs **Allow private addresses** under **Connection options** when you connect it.

A gitlab.com sign-in token lasts two hours. marotte renews it with the refresh token GitLab issues with it, so the account stays connected. If GitLab issued no refresh token or refuses a renewal, the account shows **Reconnect** once the token expires.

marotte checks each connected account in the background about once a minute, whether or not a page is open. A network failure, a rate limit or a forge outage does not disconnect the account. Sources shows a note under it, and the note goes once a later check succeeds.

When the forge rejects the token, the account shows **Reconnect**, and only a new sign-in brings it back. When the forge refuses the account instead, for example for a missing permission or an IP allowlist, the account shows the forge's reason and **Check**. Press **Check** once you have fixed it on the forge.

In both cases marotte stops giving git that account's credential, so git uses your other credential helpers or asks you. Both states survive a restart, and the **Pull requests** tab lists the account with what to do. After a restart a refused account shows a general reason in place of the forge's, and **Check** asks the forge again.

marotte 0.15.0 does not keep the forge accounts that 0.14 or earlier saved. After that update, Sources lists no accounts. Add and sign in to each one again, including the address and **Connection options** of a self-hosted forge.

Signing in to GitHub Enterprise or a self-managed GitLab uses an OAuth application registered on that server, and the connect form asks for its client ID. On GitLab, an administrator registers it on the **Applications** page. Select the `api` scope, enter any HTTPS redirect URI, leave **Confidential** unticked and tick **Device authorization grant**. Without that last box, GitLab refuses the sign-in.

## Reviewing the agent's edits

- **Rewind**, the clock icon with a backward arrow at the end of a turn's footer, sends the conversation back to the message of yours that follows that turn. The agent's file edits roll back with it, from snapshots kiro-cli takes separately from git. If the message box is empty, that message's text comes back to it to edit and send again. Its attachments do not come back. Ctrl+Up, or Cmd+Up on a Mac, in an empty message box rewinds to your last message after you confirm.
- Supervised mode holds a whole turn for review instead of asking for each write. One approval lists every file the turn touched, renames and deletes included, and you keep or discard each one.
- The permissions page has a policy editor that sets allow, deny or ask for each capability, with path rules, and a box that explains what the policy would decide. One policy governs every tool call, shell commands included.

Rewind and supervised review cover the agent's file-editing tool. Changes made through shell commands or terminals still go through the policy, but nothing snapshots them, so use git for those. A held write is already on disk while you review it, so a file watcher or a dev server sees it before you decide.

## MCP servers

Add, edit and remove servers, local ones or remote ones over HTTP or SSE. Each server can block individual tools, reconnects live, and lets you browse its prompts and resources. For a server that needs OAuth, marotte registers itself automatically or takes a client ID you already have. A server waiting for you to sign in has a **Sign in** button, which replaces the credentials the server has stored. The server then shows **Signing in**, an **Open sign-in page** link and a box for pasting the address of a page that fails to load. Finish within the server's connection timeout: 60 seconds unless its timeout is set higher, up to 10 minutes. Several servers can sign in at the same time. A Google sign-in asks for offline access, so Google shows its consent screen each time and the sign-in keeps working past its first hour. When a server needs a new sign-in in the middle of a chat, every chat shows a banner naming it, such as "linear needs you to sign in.", with **Open sign-in page** and the same paste box. The banner goes away when the sign-in finishes, or after five minutes, when kiro-cli stops waiting. A sign-in that ends without a token turns the banner into a warning, and the server's next tool call asks again. If no marotte page is open in a browser, kiro-cli hears at once that nobody can open the sign-in page, so the tool call fails instead of waiting. The sign-in is kept for workflow steps too, so a step does not ask again on every run. A server from your organization's catalog has an **Edit** form with only its environment variables and headers, for values the catalog asks for, such as your own API key. A variable fills a value the catalog leaves empty, and a header replaces the catalog's header of the same name. These values are stored and hidden like those of any other server. A server that kiro-cli loaded but another layer replaced or switched off shows the same badge as a steering doc, and a server that failed to start shows its error on its card.

marotte writes this list into kiro-cli's `~/.kiro/settings/mcp.json`. If anything else changes the servers there, marotte puts them back within 30 seconds, or when a chat opens, and logs a warning naming them. Edit servers here, not in that file and not with `kiro-cli mcp add`. Switching a server on that is already on puts it back in that file if it was missing or changed.

## Tools

The **Tools** tab in **Settings** installs runtimes, language servers and command-line tools from a catalog of about 900, built from the mise and aqua registries by [tool-catalog](https://github.com/cplieger/tool-catalog). Installs run in the background. A tool can be pinned to a version. For a tool outside the catalog, install it from the terminal. Debian packages are covered in [OS packages](os-packages.md).

Version checks and some installs read GitHub's API. Without an account, GitHub allows 60 of those requests an hour from your address. Connect a github.com account on the **Sources** tab of the git panel, and marotte sends its token with them, which raises the limit. A GitHub Enterprise account is not used for this. When the limit is reached, the **Tools** tab says so, and offers to connect an account when none is connected. GitHub also limits bursts of requests, and an account does not raise that limit. For a burst, the tab gives the time to try again instead.

Turning on a language server also turns on kiro-cli [code intelligence](https://kiro.dev/docs/cli/code-intelligence/) for the workspace. The agent then gets navigation, rename and error checking from the language server, in live chats too, with no restart. The first activation saves the detected languages to `/workspace/.kiro/settings/lsp.json`. After you add a language to the workspace, delete that file, and marotte writes it again on the next start.

## Workspace configuration

The `/docs` page lists every steering doc, skill, agent, spec and hook under `.kiro`, with its header fields. It is also where you turn hooks on and off, and start, pause, resume, cancel or schedule workflow runs. A run's tab has its own composer: send the selected step a message while it runs, or answer its question, and each message shows when it was sent and when the step read it. A step that stops to wait for your message shows as a question, like a step that asks one, and its run offers no **Resume** until you answer. A paused step's header has **Mark step done** and **Mark step failed**, which end that step as finished or failed after you confirm, without answering it. While other steps of its run are still running, a paused step takes no message and no answer to its question. **Mark step done** ends it at once, but the steps after it start only when the other steps finish, or at once if you pause and resume the run, which interrupts them. While the run keeps running, the group holding it reads "Done, moves on when the run's other steps finish", or "Failed, applies when the run's other steps finish" after **Mark step failed**. If the step has already reported that it is done or failed, it says so, for example "Done, applies when the run's other steps finish", and the matching button comes first. The **+** at the top right creates a new steering doc, skill, prompt, agent or hook in the workspace's `.kiro`. Steering docs, prompts, agents and hooks start from the template the matching Kiro client writes. A skill has no Kiro template, so it starts from the name and description Kiro's skill format requires. The new file opens in the editor. On **Specs** it starts a spec chat that drafts the requirements, as `/spec new` does in kiro-cli.

A steering doc or agent that kiro-cli loaded but does not use carries a badge naming the layer that decided it: **Replaced by** a layer with an item that replaces it, or **Off by** a layer whose setting switched it off. Its tooltip gives the detail. An agent kiro-cli could not load shows the error on its row, with or without a badge. A row on the **Workflows** panel gets the same badge when kiro-cli reports its workflow as not in use. kiro-cli 2.31 reports no such workflow, so on that version no workflow row shows one.

**Run** opens a form under the workflow with its inputs and a **Model** and **Effort** choice. Above **Launch**, the form lists the workflow's steps, with their agents, models, effort levels and loop limits. The choice applies to every step that does not name its own model or effort. **Default** sends neither, so the workflow's own settings apply. A schedule keeps its own choice for every run it starts. When you launch or save, marotte refuses a model or effort level your account does not offer. Without that check, kiro-cli would accept it and fail the step later.

**Run when…** on a workflow's row starts it on a schedule, or when something happens on a forge: a label added to an issue or pull request, one opened by an account you list, or a CI run that finished. [Event triggers](triggers.md) describes the forge rules, who can start a run and how a workflow handles an event that starts it twice.

A rule whose workflow file is gone stays on the **Workflows** panel, marked "Its workflow file is gone, so this rule cannot run.", with a **Delete rule** button.

If the agent engine is too busy to start a scheduled run, marotte tries again, waiting longer each time, up to 8 minutes between tries. Meanwhile the schedule's row says the run is waiting on the agent engine. If the schedule's next run time comes first, the row records the missed run as skipped because the engine was busy, and the next run starts on time.

A workflow step's file tools reach the same folders as a chat's: `/workspace`, `/uploads` for reading, and the [additional directories](configuration.md#folders-the-agent-can-use-beyond-workspace) you grant. A step can also read the edit snapshot kiro-cli writes for its own run when a workflow is edited mid-run. A step that reads any other path, such as another file under `/config/home/.kiro/sessions`, fails with `path escapes workspace`, so write that step to read the file with a shell command.

A `command` or `background-process` watch runs its command outside any tool call, so no `PreToolUse` hook sees it. A hook that blocks a shell command, such as a `git push`, does not stop the same command in a watch's command line. Put a command a hook must check in a step instead.

Instructions for every chat and knowledge bases are under **Custom instructions** in **Settings**, and **Settings** also has a diagnostics report you can copy. **Data sharing** on its **General** tab holds the **kiro-cli telemetry** switch, one switch for kiro-cli's usage telemetry and its legacy toolkit telemetry. It is on by default, as in kiro-cli, and an enterprise organization's usage-analytics setting overrides it. The sidebar shows your account's usage and switches between light, dark and system themes. The prompt bar shows the current chat's context use and credits. Open tabs follow you to every device, while each device keeps its own active tab, shell panel height and sidebar width.

## Knowledge bases

The agent can search local folders you index for it under **Knowledge bases** on the **Custom instructions** tab in **Settings**. The field takes a folder path, never a URL, either absolute or relative to `/workspace`. Clone the repository first, then index the folder that holds its markdown.

```sh
git clone --depth 1 https://github.com/rust-lang/book /workspace/refs/rust-book
```

Then add `refs/rust-book/src`. Trees like these index well, because every page is a plain markdown file.

| Project | Folder | Pages |
| --- | --- | --- |
| [rust-lang/book](https://github.com/rust-lang/book) | `src` | 112 |
| [astral-sh/uv](https://github.com/astral-sh/uv) | `docs` | 81 |
| [prometheus/docs](https://github.com/prometheus/docs) | `docs` | 71 |
| [reactjs/react.dev](https://github.com/reactjs/react.dev) | `src/content` | 223 |
| [kubernetes/website](https://github.com/kubernetes/website) | `content/en/docs` | 1709 |

Index a subfolder, not a repository root, so the index skips code and assets. Indexing runs in the background and the row shows a percentage. A few hundred pages take minutes, and a tree the size of [mdn/content](https://github.com/mdn/content), with 14,000 pages, takes far longer.

## Notifications

marotte can be installed as an app from the browser. It then sends notifications when a turn finishes, a pull request's checks settle, a workflow run ends or stays paused because marotte stopped resuming it, a scheduled or triggered run cannot start, or the agent needs permission, even with the tab closed. Browsers allow this only over HTTPS or on `localhost`.

The turn, pull request and workflow run notifications each have a switch on the **General** tab in **Settings**. Turns and workflow runs are on by default. Pull requests are off by default, because the forge already shows their checks. Pull request notifications work on GitHub, GitLab, Gitea, Forgejo and Codeberg, once the pull request's CI reports a result. The permission notice has no switch, because nothing else tells you off-screen that a turn is waiting on you.

A scheduled run cannot start when its launch fails, when the Kiro sign-in is missing or unreachable for more than 3 minutes past the run time, or when the agent engine stays busy until the schedule's next run time. The notification comes under the workflow run switch and opens the **Workflows** panel. It comes once, when a schedule starts failing. After a run that failed or did not start, the next runs that do not start send nothing until a run completes. A run that starts and then fails sends its own workflow run notification instead. An [event rule](triggers.md) notifies the same way once its launches start failing, and not again while they keep failing, until one of its runs starts or you edit or resume the rule.

A device still receiving the live stream gets no push. Its open page shows the notification itself, unless the chat or run it is about is the tab on screen. A request raised within about 30 seconds of locking a phone is held and sent once the stream goes quiet. It is dropped if someone answers it elsewhere or its time runs out first.

The number on the browser tab's title and the installed app's icon counts what wants you: an open question or permission request, a paused workflow run, and finished chats and runs you have not looked at. An open question counts until you answer it, even on the chat you are reading. marotte remembers what you have looked at, so reading a chat on one device clears it on your others. A device with marotte open updates when the server's next update reaches it. A backgrounded or closed app updates the next time you open it. A retried workflow run counts again when it finishes, unless the retry only re-ran terminal watches or the run was launched outside marotte.
